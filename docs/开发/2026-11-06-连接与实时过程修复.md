## BUG-27：蜂窝网、Wi-Fi 与切网恢复

确认的实现缺口：Android 默认网络回调原先只更新自定义接口枚举，随后调用已经启动的 `NativeNetwork.start()`（节点存在时直接返回），没有唤醒 Tailscale 的网络监视器。上游 v1.104.1 在 Android 上的兜底网络检查间隔为 10 分钟。原先持续 NoState 后每两分钟停止并重建节点，也会丢掉正在恢复的控制面连接和网关。

本次将网络可用、丢失、地址变化传入原生层；配置实际变化后通知 Tailscale 的网络监视器立即重新检查。重复配置不触发重绑，保留设备登录、节点、网关和当前配对。持续 NoState 不再循环销毁节点。Flutter 收到切网通知后重建当前电脑连接和事件订阅。

此前手机 shell 中单个 controlplane TCP 端口超时只说明那次探测失败，不能证明运营商阻断，也不能独立证明是 NoState 的唯一原因。内置 tsnet 使用用户态网络，不创建 Android 系统 VPN；无活动 VPN 和 shell 不能直接访问 Tailscale IP 也不是 App 链路失败的独立证据。本轮以 App 画面、认证请求和会话列表响应确认实际连接。

## 冷启动蜂窝 NoState：双栈解析缺失（手机 0.1.36）

本次进一步证据：手机系统解析 controlplane.tailscale.com 仅返回 192.200.0.x，IPv4 TCP 443 超时，系统 IPv6 查询报告无法解析。但直接向当前网络的运营商 DNS 211.137.191.27 / 218.201.96.131 发 AAAA 查询均返回 2606:b740:49:: 地址；手机保留原 HTTPS 域名、正常验证证书，连接其中 IPv6 地址 HTTP 200（TLS 约 0.46 秒）。诊断程序使用同一运营商 DNS 的纯 Go 双栈解析及正常 Happy Eyeballs，不指定目标 IP，HTTPS HTTP 200（约 0.71 秒）。故本场景丢失位于系统解析路径，不应继续推断为运营商 DNS 没有 IPv6 或整个控制面不可达。

代码修正：Android 将当前 LinkProperties 的 DNS 与明确配置的 Private DNS 名称一并通知原生层；Tailscale 的基础设施解析器使用这些 DNS 查询 A / AAAA，由上游 Happy Eyeballs 选择链路。DNS 信息跟随网络回调更新，不写死控制服务器 IP，不改控制服务器域名；明确配置的 Private DNS 保留 TLS 和证书校验。电脑服务保持 0.3.22，手机构建 0.1.36（2038）。此前切网成功不能覆盖冷启动场景，此次需以实际冷启动核对结果为准。
