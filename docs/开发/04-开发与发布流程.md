# 开发与发布流程

依据本次讨论整理的协作约定：想法先进入需求和流程确认，集中开发，测试后提供验收包，再正式发布。以下模板与门槛作为后续执行基线。

## 一轮迭代

| 阶段 | 需要完成的事情 | 进入下一阶段的依据 |
| --- | --- | --- |
| 收集 | 写目标、场景、现象、预期；进入需求池 | 能明确描述要解决的问题 |
| 需求 | 确定本版范围、不做内容、验收条件 | 用户确认范围，未决项显式列出 |
| 流程与原型 | 页面入口、操作、返回和异常状态 | 用户确认有变化的流程与界面 |
| 技术检查 | 确认助手能力、接口、数据、权限和迁移影响 | 方案可行，风险已记录 |
| 开发 | 按验收条件实现，新增想法进入需求池 | 本版功能完整、自测通过 |
| 验收 | 执行适用自动检查和真机主流程，提供内部验收包 | 无阻塞缺陷，用户体验确认 |
| 发布 | 固定版本、记录变化、产物校验与恢复方式 | 验收通过后发布，保留记录 |

小修复可以在同一个需求条目内完成简短评审，无需每次制作完整设计稿。文档整理和原型评审不需要打 APK；功能需要真机体验时提供明确用途的内部包。

## 需求条目模板

```text
编号 / 标题：
提出日期 / 来源：
用户场景与问题：
预期行为：
本版包含 / 不包含：
受影响页面 / 助手：
正常流程 / 异常流程：
验收条件：
状态：待确认 / 已确认 / 开发中 / 待验收 / 已完成 / 延后
关联代码、截图、验证记录：
```

## 测试与验收

按改动选择检查：服务端或 Web 的 `npm run typecheck`、适用 `npm test`、`npm run build`；Flutter 的 `flutter analyze`、`flutter test`；涉及原会话/附件/网络的改动需补适用真机验证。文档修改只检查内容、链接与一致性，不为了文档生成安装包。

每次验收记录版本、设备、连接方式、用例、结果和未覆盖项；模拟测试、接口测试、真机验收分别记录。测试仅在专用会话开展，涉及实际消费重置卡等操作需单独明确安排。

最低回归范围按影响选择：启动与配对恢复、打开历史、新建/发送/停止、断线恢复、只读权限、受影响助手、附件和用量。未通过的项目写成缺陷；未测项目写“未验收”，不写成已通过。

## 版本与变更管理

- 新想法先记入需求池；影响本轮目标或阻塞缺陷才插入当前范围，并更新验收条件。
- 安装包区分内部验收与正式发布，记录电脑服务和手机版本的对应关系。
- 正式发布前确认安装版可独立运行，不能仅用源码预览服务通过测试作为分发依据。
- 发布记录写本版变化、已知问题、安装/升级方式与恢复方式；保留上一版产物及校验值。
- 完成后同步需求状态、原型变化、使用手册及验证记录，避免文档长期落后。
